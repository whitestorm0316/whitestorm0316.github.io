# 账上少了三万七，一次对账差异的完整排查

早上九点，资金对账任务报了一条告警：账外核对差异 37240.00 元，方向是「渠道出款 > 本地记录」。

意思是云账户真的付出去了三万七，我们账上找不到对应的付款记录。这种告警优先级最高，因为它意味着钱可能已经不在我们控制之下了。

## 第一步：确认差异是真的

对账告警本身也可能是假的。先排除几种常见误报：

- 时区问题。渠道回单按 UTC 日期，我们按北京时间，跨天的交易会被算到不同日期。查了一下，渠道回单是北京时间，排除。
- 回单延迟。T+1 早上跑对账，渠道当天凌晨的付款可能还没出现在回单文件里。但这次差异是「渠道多、我们少」，回单延迟应该导致相反方向，排除。
- 汇总口径。把渠道回单按批次号聚合，和我们这边的批次记录逐笔对。

diff 结果出来了，指向一个批次：批次 `PAY-20261027-003`。渠道显示这个批次付出 37240 元，本地批次记录只有……没有这个批次。

## 第二步：本地为什么没有这个批次

查批次表：

```sql
SELECT * FROM pay_batch WHERE batch_no = 'PAY-20261027-003';
-- 0 rows
```

奇怪。批次号是我们生成的，渠道不可能凭空造一个。

翻应用日志，搜这个批次号。找到了：

```text
2026-10-27 14:22:31 INFO  batch created batch_no=PAY-20261027-003 count=42 amount=3724000
2026-10-27 14:22:33 ERROR submit to channel failed: context deadline exceeded
2026-10-27 14:22:33 WARN  batch marked FAILED, will retry
```

批次创建过，提交渠道时超时，被标记为失败。

继续查这个批次后来的状态：

```text
2026-10-27 14:35:10 INFO  batch retry batch_no=PAY-20261027-003 attempt=1
2026-10-27 14:35:11 INFO  batch submitted batch_no=PAY-20261027-003 channel_accepted=true
```

重试成功了。那本地为什么查不到？

## 第三步：重试逻辑把批次号换了

翻重试代码，看到了这段：

```go
func retryBatch(ctx context.Context, batchID int64) error {
    batch, err := repo.GetBatch(ctx, batchID)
    if err != nil { return err }

    // 重新生成批次号！
    newBatchNo := generateBatchNo()
    batch.BatchNo = newBatchNo
    batch.Status = BatchPending
    return repo.Save(ctx, batch)
}
```

重试时重新生成了批次号。第一次提交实际上**已经到渠道了**（超时只是响应没回来），渠道拿着旧批次号 `PAY-20261027-003` 付了钱。本地重试换了新号 `PAY-20261027-004`，渠道把它当成新批次又付了一遍。

两笔钱都付出去了。对账只看旧批次号，发现本地没有；如果看金额汇总，还会发现有笔重复付款。

这是一个典型的「超时不等于失败」问题。HTTP 客户端超时只说明我们没收到响应，请求可能已经到达服务端并执行成功。

## 第四步：止血

第一步是确认资金状态。联系渠道，按旧批次号和新批次号分别查询：

- `PAY-20261027-003`：已付款，42 笔，37240 元
- `PAY-20261027-004`：已付款，42 笔，37240 元

确实重复付了。

紧急处理：

1. 冻结所有待重试的批次，停止自动重试。
2. 联系渠道，看能否撤回未结算的款项（已经结算的撤不回来，只能协商下次抵扣）。
3. 检查有没有节点主收到两笔钱，如果有，从下期分成里扣回。

万幸的是，那 42 个节点主的账户状态都还是冻结中——因为我们这边的回调没处理成功，钱包没有确认扣减，所以用户也没法提现。这批钱还在渠道侧，追回有希望。

## 第五步：改代码

重试逻辑的核心错误是「换号」。改成：

```go
func retryBatch(ctx context.Context, batchID int64) error {
    batch, err := repo.GetBatch(ctx, batchID)
    if err != nil { return err }

    // 批次号不变，状态机控制可重试状态
    if batch.Status != BatchFailed && batch.Status != BatchTimeout {
        return ErrInvalidBatchState
    }

    // 重试前先查单，确认渠道是否真的没收到
    result, err := channel.QueryBatch(ctx, batch.BatchNo)
    if err == nil && result.Exists {
        // 渠道已经有这笔了，直接按查询结果推进本地状态
        return syncBatchResult(ctx, batch, result)
    }

    batch.Status = BatchPending
    return repo.Save(ctx, batch)
}
```

三点改动：

**批次号终身不变**。它是幂等键，重试时换号等于放弃幂等保护。

**重试前先查单**。超时状态不能直接重提，先问渠道有没有收到。收到了就按结果推进本地状态，没收到才重提。

**用状态机而不是布尔标记**。批次状态有明确的流转路径，任何跃迁都要校验前置状态。

## 第六步：补上监控

这类问题最怕的是「悄悄发生，月底才发现」。加了三个告警：

1. 同一批次的提现订单，在渠道侧出现两次以上付款记录。
2. 提交超时后，重试前没有查单记录。
3. 账外对账差异超过 100 元，无论方向，立即告警。

第三条是通用兜底。资金类的差异，不管多小，都不该等到月度对账才暴露。

## 事后想想

这次没有造成实际损失，很大程度是运气——用户账户还没解冻，钱还在渠道侧。如果重试发生在回调成功之后、用户提走钱之后，追回难度就完全不一样了。

「超时当失败」这个错误，在资金系统里能导致的后果比想象中严重。它不只是一个技术细节，是会把真实资金置于风险中的设计缺陷。从那以后我写重试逻辑，第一反应是「如果请求其实成功了呢」。
