# EVM 充值监听与 Reorg 冲正：唯一约束与反向流水

> 链上确认不是终态。区块会重组，事件会重放，扫码任务会重复执行——充值入账必须在这些混乱之上保持账实一致。

## 一、扫描链路

```text
 RPC 拉区块 → 解析 receipts / logs → 匹配 ERC20 Transfer → 入账
      ↑
  持久化扫描高度 + blockHash
```

扫描器持久化「已处理区块高度 + 区块哈希」。每扫一个新块，先用父哈希校验与本地记录是否连续；不连续就说明可能发生链重组，进入 reorg 处理流程。

## 二、幂等：唯一约束是第一道防线

ERC20 充值的唯一键由四个字段构成：

```sql
UNIQUE (chain_id, tx_hash, log_index, contract_address)
```

这四个字段组合唯一标识一条 Transfer 事件。重复扫描、事件重放、多个扫描实例并发写入，都会被唯一约束挡住。捕获唯一键冲突后按「已处理」返回，而不是报错中断。

注意 `log_index` 不能省——一笔交易里可能有多条 Transfer 事件（比如经过路由合约的转账），只用 tx_hash 会漏掉后续事件。

## 三、Reorg：回滚到共同祖先

检测到链重组后：

1. 从当前高度向前回溯，比较本地保存的 blockHash 与链上最新区块的 blockHash，找到**共同祖先**。
2. 回滚共同祖先之后的所有充值记录。
3. 重新扫描这段高度的区块，按新主链重建入账记录。

关键设计：**回滚不是删除**。每条充值对应一条反向资金流水，冲正时追加一笔金额为负的流水，并标记原流水为已冲正。数据库里保留完整的「原本入账 → 因 reorg 冲正 → 新链重新入账」历史链。

这么做有两个理由：一是审计要求账务记录不可篡改；二是如果冲正后重新扫描又遇到新的 reorg，历史链仍然能解释每一步的来源。

## 四、确认数与最终性

入账策略采用「达到 N 个确认后入账」。Reorg 深度超过 N 的情况极罕见，但流程仍然保留——不是因为常见，而是因为一旦发生，人工补账的成本远高于实现这套机制的成本。

## 五、Gas 成本单独记账

扫描器自身会产生 RPC 与索引成本，热钱包归集会产生 gas。这些费用不混进用户余额，而是独立计入平台成本科目，按链、按交易类型分摊。否则链上链下对账时，Gas 差异会被误判为充值漏记。

## 六、可观测性

三个核心指标进 Prometheus：

- **扫描高度**与链头高度的差值：差值持续扩大说明扫描卡住。
- **Pending 时长**：交易提交后长期未确认，可能是 gas 定价过低。
- **热钱包余额**：低于阈值告警，避免提现全部卡住。

## 小结

链上数据的正确性不来自「读取时是对的」，而来自「出错后能被发现和修复」。唯一约束管住重复，反向流水管住回滚，对账机制管住遗漏——三者组合，才敢把真实资产记进数据库。
