# EVM 充值的确认数与重组处理

充值入账前要等多少个确认，是个需要权衡的问题：确认数越大越安全，用户到账越慢。这篇讲确认数怎么定、怎么算，以及链重组之后怎么处理。

## 确认数怎么定

交易被打包进区块不代表最终确定。节点可能切到另一条更长的链，原来那个区块里的交易就消失了。等 N 个确认，本质是等重组深度超过 N 的概率低到可以接受。

不同链的差别很大，不存在通用数字：

| 链 | 出块时间 | 常见确认数 | 大致等待 |
|---|---|---|---|
| Ethereum | 12s | 12 | 约 2.4 分钟 |
| BSC | 3s | 15 | 约 45 秒 |
| Polygon | 2s | 64 | 约 2 分钟 |

这些是经验值，不是标准。定数字的方法是在目标链上统计历史重组深度分布，取一个覆盖绝大多数情况的值，再加余量。新链上线前至少拉几个月的链上数据来看。

确认数只是把风险窗口压缩，不是保险。真正的兜底是重组检测和冲正机制。

## 确认数的计算

一个容易写错的地方：确认数 = 链头高度 - 交易所在区块高度 + 1。

```go
func confirmations(head, block uint64) uint64 {
    if head < block {
        return 0
    }
    return head - block + 1
}
```

交易就在链头区块里时，确认数是 1 不是 0。这个差一会导致充值晚一个块到账，或者提前一个块入账。

更稳妥的是不只比高度，还拿那个高度的区块哈希和本地记录比对：

```go
block, err := client.HeaderByNumber(ctx, new(big.Int).SetUint64(txBlock))
if block.Hash() != storedHash {
    return ReorgDetected
}
```

只比高度发现不了「同高度不同内容」的重组。在出块快的链上，一两个块的重组很常见，高度检查会完全漏掉。

## 重组处理流程

检测到重组后的步骤是固定的：

1. 从链头往回扫，找到本地哈希和链上哈希一致的高度，即共同祖先；
2. 共同祖先之后的本地记录全部作废；
3. 对这些区块里的充值交易写反向流水，冲正余额；
4. 按新主链重新扫描这段高度。

顺序很重要：**先冲正，再重扫**。反过来会出现余额先增加再扣减，中间时刻如果发生提现，就可能超提。

冲正不删原记录，而是追加一条负数流水，并标记原流水状态：

```sql
UPDATE credit_ledger SET status = 'REORGED' WHERE tx_hash = ?;

INSERT INTO credit_ledger (tx_hash, amount, direction, reorg_of)
VALUES (?, ?, 'DEBIT', ?);
```

审计时能看到完整链路：钱进来过，因为链重组被冲掉，后来在新链上又进来了。直接删掉重写，这条链就断了。

## 用金额和去向调节风险

确认数不一定全平台一刀切。可以按业务维度分层：

- **小额充值**：降低确认数，快速到账，同时压低单日充值和提现额度；
- **大额充值**：完整确认数，必要时人工审核；
- **充值后不提现**：确认数可以低一些，资金还在平台内，风险敞口小；
- **充值后立即提现**：等满确认数，并走独立风控。

本质是用金额和资金去向来调节风险敞口，而不是只依赖一个全局确认数。

## 监控什么

配置是静态的，链是活的，上线后要看的是运行态指标：

- 待入账交易的确认数分布，有没有大量卡在阈值附近；
- 重组检测触发次数，按链统计，突然升高说明链或节点出了问题；
- 冲正流水笔数和金额，正常应接近 0，上涨就告警；
- 扫描高度和链头的差值，持续扩大说明扫描跟不上出块。

这几个指标比「当前确认数配了多少」有用得多。
