# 充值的确认数不是拍脑袋定的

「充值多少个确认才入账」这个问题，很大程度上决定了用户等多久能拿到钱，也决定了 chain reorg 的时候我们会亏多少。

## 先说结论

不同链差别很大，不存在一个通用数字。

| 链 | 出块时间 | 常用确认数 | 大致等待 |
|---|---|---|---|
| Ethereum | 12s | 12 | ~2.4 分钟 |
| BSC | 3s | 15 | ~45 秒 |
| Polygon | 2s | 64 | ~2 分钟 |
| Arbitrum | ~0.25s | 必须等 L1 最终性 | 分钟级 |

这些数字不是标准，是经验值。真正的依据是「这条链上多深的 reorg 在历史上出现过」。上线前至少拉三个月的链数据，统计重组深度分布，取一个覆盖 99.9% 情况的值再加一点余量。

## 为什么不能只等一个确认

EVM 里交易被打包进区块不代表最终确定。节点可能切到另一条更长的链上，原来那个区块里的交易就消失了——这笔充值在账上记过，但链上不存在了。

我们踩过一次：测试网上设了 3 个确认，某次 reorg 深度到了 5，有两笔充值已经入账并且用户提走了。最后只能记坏账。

从那以后入账策略改成两段：

```text
区块进入扫描器 → 达到 N 个确认 → 标记 CREDITED
                        ↓
                  后续检测 reorg → 冲正
```

确认数不是保险，只是把风险窗口压缩到可接受范围。真正的兜底是 reorg 检测和冲正机制。

## 确认计数怎么算

一个容易写错的地方：确认数 = 当前链头高度 - 交易所在区块高度 + 1。

```go
func confirmations(head, block uint64) uint64 {
    if head < block { return 0 }
    return head - block + 1
}
```

交易在链头区块里，确认数是 1，不是 0。这个 off-by-one 看着小事，实际会导致充值晚一个块到账，或者提前一个块入账。

更稳妥的做法不是只比较高度，而是重新拿那个高度的区块哈希和本地记录的哈希比对：

```go
block, err := client.HeaderByNumber(ctx, new(big.Int).SetUint64(txBlock))
if block.Hash() != storedHash {
    // 高度没变但哈希变了，说明这个高度被重组过
    return ReorgDetected
}
```

只比高度会漏掉「同高度不同内容」的重组。BSC 这类出块快的链上，一两个块的重组很常见，高度检查根本发现不了。

## Reorg 深度超过确认数怎么办

这是最坏情况，但必须处理。流程是：

1. 从链头往回扫，找到本地记录哈希和链上哈希一致的那个高度——共同祖先。
2. 共同祖先之后的所有区块，本地记录全部作废。
3. 对每个作废区块里的充值交易，写一笔反向流水冲正用户余额。
4. 按新主链重新扫描这段高度。

顺序很重要：**先冲正，再重扫**。反过来会出现用户余额先增加再扣减，中间时刻如果恰好发起提现，就形成超提。

冲正流水不能删除原记录，而是追加一条负数流水，并标记原流水的状态：

```sql
-- 原流水保持不动
UPDATE credit_ledger SET status = 'REORGED' WHERE tx_hash = ?;

-- 追加冲正
INSERT INTO credit_ledger (tx_hash, amount, direction, reorg_of)
VALUES (?, ?, 'DEBIT', ?);
```

审计时能看到完整的来龙去脉：这笔钱进来过，因为链重组被冲掉了，后来在新链上又进来了。如果直接删掉重写，这条链就断了。

## 用户体验的取舍

确认数越大越安全，但用户等得越久。ERC20 充值是业务里最常见的一类，用户习惯是「转完账立刻看到余额」。

我们的折中方案是分层：

- 小额充值：降到 6 个确认，快速到账，但单日充值上限和提现额度都压低。
- 大额充值：完整确认数，必要时人工审核。
- 已充值未提现的资金：确认数要求可以低一些，因为钱还在平台里，风险可控。
- 充值后立刻提现：必须等满确认数，且提现走独立风控。

这套规则的本质是：**用金额和资金去向来调节风险敞口**，而不是全平台一刀切一个确认数。

## 监控要看的不是确认数

上线后真正有用的指标是：

- 每个待入账交易的确认数分布，有没有大量卡在 N-1 的。
- Reorg 检测触发次数，按链统计。突然升高说明节点或者链出了问题。
- 冲正流水笔数和金额，这个数字正常应该是 0 或者极小。一旦上涨立刻告警。
- 扫描高度和链头的差值，持续扩大说明扫描跟不上了。

这些指标比「当前确认数配置是多少」有用得多。配置是静态的，链是活的。
