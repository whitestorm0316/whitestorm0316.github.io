# 结算跑批崩在凌晨三点，水位到底该记在哪

那天凌晨三点报警，算账任务挂了。重启，跑到一半又挂在同一个节点上。

问题出在「从哪继续」。最开始写得很直觉：任务表里记一个 `last_node_id`，每次从 `node_id > last_node_id` 开始扫。挂了就从上次的 ID 往后跑，听上去没毛病。

实际上这个设计至少有三个洞。

第一个，节点 ID 不是按时间有序的。凌晨补报的节点、刚上线的节点、被踢掉又重新加进来的节点，ID 分布是散的。按 ID 递增扫，等于默认「ID 大的数据才新鲜」，但结算关心的是账期，不是 ID。

第二个，晚到数据。账期截止点用入库时间冻结，但截止前最后几分钟进来的数据会落到已经算过的节点上。如果水位已经越过那个节点，这批数据就永远进不了当期的账。

第三个最要命：规则版本。同一个账期，如果规则从 v1 切到 v2，重算时要覆盖的是 v1 的结果，而不是跳过。水位不变、版本变了，处理逻辑完全不一样。

后来改成这样：

```sql
CREATE TABLE settle_task_state (
  period       VARCHAR(7)  NOT NULL,
  shard_no     INT         NOT NULL,
  rule_version INT         NOT NULL,
  status       TINYINT     NOT NULL,  -- 0待跑 1跑完 2失败
  row_count    INT         DEFAULT 0,
  updated_at   DATETIME    NOT NULL,
  PRIMARY KEY (period, shard_no, rule_version)
);
```

分片按 `node_id % N` 取模，和节点大小无关，纯粹是为了把 4300 万条摊开。每个分片算完，在同一个事务里写结算明细和状态行：

```go
err := db.Transaction(func(tx *gorm.DB) error {
    if err := tx.CreateInBatches(bills, 500).Error; err != nil {
        return err
    }
    return tx.Exec(`
        INSERT INTO settle_task_state (...)
        VALUES (?, ?, ?, 1, ?, NOW())
        ON DUPLICATE KEY UPDATE status=1, row_count=VALUES(row_count)
    `, period, shard, version, len(bills)).Error
})
```

这里有个容易被忽略的点：**明细写入和状态标记必须同一个事务**。分开写的话，中间崩溃就会出现「明细已落、状态未落」，重启重跑一遍，虽然结算单有唯一键能挡住重复，但白白多算一遍；反过来的顺序更糟，状态标完成、明细没写，钱就漏了。

失败重试不是简单的 `for i := 0; i < 3; i++`。凌晨那次挂掉的原因是 ClickHouse 那边一个分片查询超时 120 秒，任务整体超时被 kill。重试策略改成指数退避 + 单分片超时，并且把失败的分片单独标 2，而不是让整个账期一起重来：

```go
backoff := []time.Duration{0, 10 * time.Second, 30 * time.Second, 90 * time.Second}
for attempt, d := range backoff {
    if d > 0 { time.Sleep(d) }
    ctx, cancel := context.WithTimeout(ctx, 110*time.Second)
    err := runShard(ctx, period, shard, version)
    cancel()
    if err == nil { break }
    log.Warn("shard failed", "period", period, "shard", shard,
             "attempt", attempt, "err", err)
}
```

还有个细节：分片之间不共享写集，所以可以并发跑，但并发度不能拍脑袋。我们开到 8 的时候 MySQL 那边开始出现锁等待，降到 4 反而总耗时更短。这个数字没有通用答案，得看自己的库和表结构。

至于晚到数据，现在的做法是账期截止后留一个 T+1 的尾巴窗口，尾巴窗口内的数据走「补算」流程，生成的是调整单而不是改原结算单。尾巴窗口关掉之后还来的，人工介入。这条规则写进结算规则文档里，比写进代码更重要——代码能挡住重复，挡不住业务方一句「就这一笔你帮我改一下」。

那次故障最后的根因其实很土：ClickHouse 一个节点的磁盘快满了，查询慢到超时。水位设计的问题是被它带出来的。但如果没有那次崩，我们大概还会用 `last_node_id` 跑很久，直到某天对账发现某个节点少了一笔。
