# T+1 结算引擎：算账与入账两阶段解耦

> 算账可以重跑一百次，入账只能执行一次。把这两种语义混在一个事务里，是结算系统最常见的坑。

## 一、为什么要拆成两阶段

结算做的事情看似简单：把账期的流量数据变成节点钱包里的钱。但它同时具有两种完全相反的性质：

- **算账**：计算密集型，结果应该可重复、可验证，出错要能重跑覆盖。
- **入账**：资金操作，有副作用，重复执行就是重复付款，必须严格只执行一次。

把它们放在同一个流程里，重跑逻辑就会变成一场噩梦：要么为了避免重复付款而不敢重算，要么重算时把已经付过的钱又记了一遍。所以引擎被拆成两个阶段，中间用结算单作为契约。

## 二、阶段一：算账

```go
type BillKey struct {
    Period      string // 账期 2026-01
    NodeID      int64
    RuleVersion int    // 规则版本，显式传入
}
```

算账任务按 `(账期 + 节点 + 规则版本)` 做唯一键，结果 upsert：

- 同一组键重跑，覆盖明细，不产生任何资金副作用。
- 规则版本显式传入，不读「当前配置」——这是上一篇文章强调的复现性要求。
- 算完后生成结算单，状态置为 `CALCULATED`，金额字段全部确定。

这个阶段可以随便重试、并行、按节点分片，失败了重来即可。

## 三、阶段二：入账

入账只做一件事：把 `CALCULATED` 状态的结算单，变成钱包余额变动 + 资金流水。

```sql
UPDATE settlement_bill
SET status = 'POSTED'
WHERE bill_no = ? AND status = 'CALCULATED';
-- 影响行数为 0 说明已处理过，直接返回
```

靠结算单号的唯一约束 + 状态条件，保证**并发重复触发、定时任务重入、机器重启重试**都只会成功一次。入账涉及的多表写入放在同一数据库事务内，余额与流水要么一起成功要么一起回滚。

## 四、金额：全链路整数分

从计量结果到结算单、到钱包余额、到代付指令，金额一律用 `int64` 存储「分」。浮点在这个链路里没有任何位置——0.1 元的二进制误差乘以千万级账单，就是真实的资损。展示层再统一格式化为元。

## 五、状态机与调整单

```text
INIT → CALCULATED → POSTED → ADJUSTED
```

**已经入账的账单不直接修改。** 发现差异（晚到数据、规则修正、对账差异）时，生成一张关联的调整单，金额可正可负，走独立的入账流程。这样做的好处是历史账单永远可追溯，审计时看到的是一条完整的变更链，而不是一个被覆盖后的终值。

## 六、批处理工程细节

- T+1 凌晨触发，按节点 ID 分片，控制单批规模，避免一次事务锁住过多行。
- 算账与入账之间加一致性校验：结算单金额合计 == 明细金额合计，不等则不进入入账阶段并告警。
- 任务记录 `period + 阶段 + 分片` 的执行水位，支持从失败分片续跑，不需要从头再来。

## 小结

两阶段解耦的本质是**把「可以重试的计算」和「不可重试的动作」物理隔开**，中间用带唯一约束的结算单做闸门。这套结构后来在钱包、支付的每个环节都被复用了一遍。
