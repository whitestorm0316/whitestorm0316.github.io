# 钱包账务：四态余额与双写流水的幂等设计

> 余额是一个数字，但钱包系统真正要管理的是「这个数字为什么变成这样」。答案是：余额与流水双写，状态机约束每一次变更。

## 一、四种余额状态

节点主的钱不是到账就能拿走，账期结算后有一段在途时间。账户因此被拆成四个逻辑态：

| 状态 | 含义 |
|---|---|
| 可用 | 可以发起提现 |
| 冻结 | 已锁定，等待支付结果 |
| 在途 | 已提交代付，等待渠道回执 |
| 待结算 | 已算账未入账 |

四态之和等于账户总余额。每一条资金流水都明确记录**从哪个状态到哪个状态、变动多少**，而不是笼统地记一笔「收入/支出」。

## 二、余额与流水双写

```text
账户表 accounts        余额快照：available / frozen / in_transit / pending
流水表 account_ledger  每笔变动：biz_no / account / direction / from / to / amount
```

两表在同一数据库事务中写入。流水的唯一键由 `业务单号 + 账户 + 方向 + 状态动作` 构成，重复请求撞唯一键就直接返回成功，天然幂等。

流水里保留业务单号，意味着任何一笔余额变化都能反查到它的来源：是结算入账、是提现冻结、还是失败解冻。`balance(t) = balance(0) + Σ ledger` 这个等式必须随时成立。

## 三、状态机约束变更路径

```text
待结算 ──入账──→ 可用 ──提现申请──→ 冻结 ──提交代付──→ 在途
                  ↑                  │                │
                  └────失败解冻───────┘       成功──→ 扣减
                                              失败──→ 解冻
```

代码层面不允许「可用直接扣减」这种绕过状态的操作。所有变更入口收敛到少量几个方法，每个方法先校验当前状态，再执行带状态条件的更新：

```sql
UPDATE accounts
SET available = available - ?, frozen = frozen + ?
WHERE account_id = ? AND available >= ?;
```

条件不满足就返回失败，由上层决定重试还是拒绝。这比「先查再改」安全得多——并发下不会出现超扣。

## 四、失败自动解冻

对私代付的链路是异步的：审核 → 批次 → 指令 → 渠道回调。提现申请时冻结余额，提交渠道后转在途。**只有收到渠道的成功回执才真正扣减**；失败或超时则在确认后自动解冻回可用。

这里的幂等关键是：回调可能丢失，也可能重复送达。所以查单任务定时兜底，而解冻动作本身也走带状态条件的更新——已经扣减过的单子，重复解冻不会把钱「变出来」。

## 五、每日快照与重建

每天对全部账户做余额快照，并用当日流水序列从昨日快照重建余额，两者比对。这是发现「余额被绕过流水直接修改」这类问题的唯一可靠手段。

在此之上做三层账实核对：

- 余额快照 ↔ 资金流水（账内核对）
- 结算单金额 ↔ 钱包入账流水（业务与账务核对）
- 钱包出账流水 ↔ 代付回单（账务与外部资金核对）

## 小结

钱包系统里，**唯一键、事务、状态机**这三样东西承担了绝大部分正确性责任。余额只是它们的计算结果。把流水设计成「可重建余额」的账本，才敢在出现问题时说：我们的钱没有丢，只是需要重算一次。
