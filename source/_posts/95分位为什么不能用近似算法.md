# 95 分位为什么不能用近似算法

有一次甲方来对数，说我们账单上某节点的带宽比他们自己统计的高了 3%。查了两天，最后发现不是流量算多了，是分位函数用错了。

计费口径是 95 峰值：一个账期里所有 5 分钟窗口的速率排序，扔掉最高的 5%，取剩下的最大值。这个数在 ClickHouse 里有三种写法：

```sql
quantile(0.95)(rate)          -- 默认值，近似
quantileTDigest(0.95)(rate)   -- t-digest，近似，内存友好
quantileExact(0.95)(rate)     -- 精确
```

我们一开始用的是 `quantile`。快，内存小，看起来没差别。问题出在重算上。

## 近似算法不保证同一批数据算出同一个值

t-digest 这类算法的核心是聚类，把相近的值合并成质心，用质心近似原分布。合并顺序会影响质心的位置和数量。同一批数据，如果写入顺序不同、并行度不同、或者 ClickHouse 在不同分片上各自算完再合并，结果可能落在不同的质心上。

对我们的影响是：账期重算一次，账单上一个数；再重算一次，差了零点几 Mbps。金额跟着变，节点主来问，我们解释不了。

`quantileExact` 的实现是把值全放进数组排序，内存 O(n)，但结果确定——同样的数据集，无论怎么分片、什么顺序，`quantileExact(0.95)` 永远返回同一个值。结算系统里，这个性质比性能重要得多。

## 一个账期到底有多少个点

按 5 分钟窗口算，一个月 30 天：

```text
30 × 24 × 12 = 8640 个窗口
```

这是单节点单账期的数据量。8640 个 float64 排个序，大概几十微秒，完全不是问题。所以「精确算法慢」这个顾虑在我们的数据量级上根本不成立。真正需要担心的是高基数场景——如果把节点、线路、账期、规则版本全部 group by，组合数上去之后内存才会吃紧。我们的做法是分批算，一个节点一个节点过，把内存压力摊掉。

## 还有一个更隐蔽的坑：速率的精度

窗口速率这样算：

```sql
up_bytes * 8 / 300
```

如果 `up_bytes` 是 UInt64，乘 8 之后还是整数，除以 300 在 ClickHouse 里会得到 Float64。不同写法的结果在小数点后十几位可能不一样，而这些微小差异经过排序后会影响分位值的选取，尤其是当两个窗口速率非常接近的时候。

我们后来统一改成：分位计算全程用整数 bps，展示层再转 Mbps。

```sql
-- 存的时候就定死口径，单位 bps，整数
toUInt64(up_bytes) * 8 / 300 AS rate_bps
```

注意这里的 `/` 在 ClickHouse 整数除法下会截断。截断是有意的——**计费口径里必须明确定义舍入发生在哪一步**，否则「数学上等价」的两种写法会算出不同的钱。

## 特殊值怎么处理

95 分位还有一个业务问题：节点离线时窗口里没有数据。

- 缺失的窗口算 0 还是跳过？算 0 会把 95 分位拉低，跳过则意味着离线不受惩罚。
- 我们的口径是：缺失窗口算 0，同时离线时长单独统计，超过阈值再叠加扣罚系数。两件事分开算，不要混进一个分位函数里。
- 异常上报（时钟漂移、重复批次）的窗口直接剔除，不进分位计算，但要留痕。

这些规则全部写进规则版本表，算账时显式加载：

```go
rule, err := repo.GetRuleVersion(ctx, period, ruleVersion)
if err != nil { return err }

rate := calc.Percentile95(windows, rule.MissingWindowPolicy, rule.OutlierFilter)
```

## 后来那 3% 的差异

回到开头那次对数。甲方自己算 95 峰值的时候，是把它统计系统里的近似分位直接拿来比。我们这边用精确分位，两边差了 3%。谁都没算错流量，是「95 分位」这个词在两个系统里的实现不一样。

最后我们把口径写进了合同附件：用哪个函数、窗口长度、缺失窗口怎么处理、舍入在哪一步。技术上的差异本来不难解决，难的是它藏在两个都叫「95 分位」的黑盒里，直到对账那天才冒出来。

从那之后，凡是涉及钱的数值计算，我都要求能写出可复现的 SQL 或代码，并且附上「同样输入必然同样输出」的验证。近似算法不是不能用，是不该用在这种地方。
