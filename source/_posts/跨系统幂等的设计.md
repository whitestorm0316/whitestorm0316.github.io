# 跨系统幂等的设计

幂等这个词在单机系统里很好实现：给表加唯一键，重复请求撞键返回第一次的结果就行。一旦链路跨出自己的数据库，唯一键就只能管住本地，管不住外部系统。

这篇聊聊跨系统场景下幂等要怎么设计，以及为什么「加个唯一键」不够用。

## 唯一键的边界

代付链路大致是这样：

```text
本地创建批次 → 提交到渠道 → 渠道异步回调 → 本地更新状态
```

本地批次表给 `batch_no` 加唯一键，能保证我们自己不会创建两个相同批次。但渠道那边会不会对相同 `batch_no` 去重，取决于渠道的实现，不能假设。

所以幂等要分两层做：

- **本地层**：批次号唯一，状态机控制哪些状态允许提交，防止本地重复发起；
- **外部层**：提交时携带我们生成的业务单号，依赖渠道按这个单号做幂等。对接渠道时要明确确认这一点——没有这个能力，就不能直接上自动化。

任何一层的缺失都会留下缺口。

## 回调重复是常态

渠道回调不保证只送一次。网络超时重试、渠道侧重推、接收方返回 5xx 都可能造成同一条回调送达多次。

如果处理逻辑是「收到成功回调 → 更新钱包余额 → 扣减冻结」，重复两次就扣两次。防御方式是把状态变更放在最前面，用状态机抢占：

```go
affected, err := db.Exec(`
    UPDATE withdrawal_order
    SET status = 'SUCCESS'
    WHERE order_no = ? AND status = 'IN_TRANSIT'
`, orderNo)

if affected == 0 {
    // 已经处理过，或状态不对，直接返回成功
    return nil
}

// 只有抢到这次状态变更的调用，才继续做账务
if err := wallet.ConfirmDeduct(ctx, orderNo); err != nil {
    alert.Critical("callback state advanced but wallet failed", orderNo)
    return err
}
```

这里的顺序是有意为之的。先改状态、后做账务，会带来一个短暂的不一致窗口（状态已成功、账务没跟上），但它是**可补偿的**——跑一次补账任务就能修复。反过来先做账务、后改状态，重复回调会重复扣款，那是不可逆的。

分布式系统里选方案，要看的不是「哪个更不容易出错」，而是「出错之后哪个能修」。

## 回调丢失靠查单兜底

重复可以挡住，丢失没有信号，只能定时查。

```sql
SELECT order_no, channel_tx_no
FROM withdrawal_order
WHERE status = 'IN_TRANSIT'
  AND submitted_at < NOW() - INTERVAL 2 MINUTE
ORDER BY submitted_at
LIMIT 100;
```

扫出来之后主动调渠道查询接口，用查询结果驱动状态机。查单和回调会并发撞到同一笔订单，状态机的 `WHERE status = 'IN_TRANSIT'` 保证只有一个生效。

查单间隔做成阶梯式：刚提交的不查（给回调留时间），2 到 10 分钟每分钟一次，10 分钟以上每 5 分钟一次，超过 1 小时转人工。太密会触发渠道限频，而且对同一笔单子反复查没有意义。

## 失败解冻也要幂等

代付失败要把冻结余额退回来。这个动作同样可能重复触发——回调说失败、查单也说失败，两个线程同时解冻。

把「是否已处理」变成一条可查询的记录，而不是一个会被覆盖的布尔字段：

```sql
INSERT INTO freeze_release (freeze_id, release_type, biz_no)
VALUES (?, 'FAIL_UNFREEZE', ?)
ON DUPLICATE KEY UPDATE id = id;
-- RowsAffected == 1 才真正执行解冻
```

这样既是幂等控制，也是审计线索：能查到是谁、在什么时间、因为哪个业务单号触发的释放。资金系统里，「能不能查到为什么」和「有没有算对」同样重要。

## 重试时的一个坑

超时不等于失败。HTTP 客户端超时只说明没收到响应，请求可能已经到达渠道并执行成功。

如果超时后直接重试提交，而重试逻辑里重新生成了批次号，渠道就会把两个不同批次各付一次。正确的做法是：批次号终身不变，重试前先查单——

```go
func retryBatch(ctx context.Context, batchID int64) error {
    batch, err := repo.GetBatch(ctx, batchID)
    if err != nil {
        return err
    }
    if batch.Status != BatchFailed && batch.Status != BatchTimeout {
        return ErrInvalidBatchState
    }

    result, err := channel.QueryBatch(ctx, batch.BatchNo)
    if err == nil && result.Exists {
        return syncBatchResult(ctx, batch, result) // 渠道已受理，推进本地状态
    }
    batch.Status = BatchPending
    return repo.Save(ctx, batch)
}
```

批次号是幂等键，换号等于主动放弃幂等保护。

## 对账是最后一道防线

前面所有机制都是「尽量不让差异发生」。差异一旦发生，靠批次对账发现：每天拉渠道回单，和本地批次明细逐笔比对，差异进差异池，人工确认后走调整单，不自动修复。

自动修复的风险在于，它无法区分「渠道延迟记账」和「真的少了一笔」。把延迟当成丢单去补付，反而制造出真正的问题。资金类操作宁可慢，不要自动。
