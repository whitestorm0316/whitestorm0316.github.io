# 结算跑批的断点续跑设计

T+1 结算是一个典型的长事务批处理：账期结束后，把几千万条流量明细按规则聚合成结算单。任务跑几十分钟是常态，中途失败也很正常——机器重启、数据库抖动、上游查询超时都可能打断它。

断点续跑要解决的问题只有一个：**任务中断后，从哪里继续，以及怎样保证已经做完的部分不会被重复写入、漏写**。

## 为什么不用 last_id 水位

最直觉的做法是记一个 `last_node_id`，下次从 `node_id > last_id` 继续。这个方案在结算场景里不成立，原因有三个。

第一，节点 ID 和账期没有单调关系。补报的节点、新上线的节点、重新激活的节点，ID 是散的。结算关心的维度是账期和规则版本，不是 ID 顺序。

第二，晚到数据。账期截止点按入库时间冻结，但截止前最后几分钟写入的数据，可能落在一个「已经扫过」的节点上。水位推进之后，这批数据就进不了当期账单。

第三，规则版本。同一个账期如果规则从 v1 切到 v2，重算时要覆盖的是 v1 的结果，而不是从水位之后重新开始。水位不变、版本变了，处理逻辑完全不同。

所以水位必须是一个多维度的复合状态，而不是一个游标。

## 分片状态表

做法是把账期切成若干分片，每个分片独立记录状态：

```sql
CREATE TABLE settle_task_state (
  period       VARCHAR(7)  NOT NULL,
  shard_no     INT         NOT NULL,
  rule_version INT         NOT NULL,
  status       TINYINT     NOT NULL,  -- 0 待跑 / 1 完成 / 2 失败
  row_count    INT         DEFAULT 0,
  updated_at   DATETIME    NOT NULL,
  PRIMARY KEY (period, shard_no, rule_version)
);
```

分片按 `node_id % N` 取模，和节点 ID 的大小无关，只用来把数据量摊开。主键里带 `rule_version`，意味着同一个账期可以有多次不同版本的完整计算结果，互不覆盖。

任务启动时先加载状态表，只跑 `status IN (0, 2)` 的分片，已完成的直接跳过。重算时指定新的版本号，所有分片从头跑一遍，旧版本结果保留可查。

## 明细和状态必须同事务

这是断点续跑最容易写错的地方。分片算完之后，结算明细和状态标记要在同一个事务里落库：

```go
err := db.Transaction(func(tx *gorm.DB) error {
    if err := tx.CreateInBatches(bills, 500).Error; err != nil {
        return err
    }
    return tx.Exec(`
        INSERT INTO settle_task_state (period, shard_no, rule_version, status, row_count, updated_at)
        VALUES (?, ?, ?, 1, ?, NOW())
        ON DUPLICATE KEY UPDATE status=1, row_count=VALUES(row_count), updated_at=NOW()
    `, period, shard, version, len(bills)).Error
})
```

分开写会出两种问题：明细写入成功、状态未更新，重启后重复计算一遍（有唯一键兜底不会重复入账，但浪费时间）；状态先标完成、明细写入失败，这部分数据就永久漏掉了。

结算明细本身还要有一层唯一约束 `(period, node_id, rule_version)`，作为最后一道防线。状态表管「跑到哪」，唯一键管「不重复」，两者职责不同，都要有。

## 失败重试的粒度

重试不是简单地对整批任务 `for` 循环三次。分片之间写集不重叠，可以独立重试，所以失败的分片单独标 2，重启后只重试失败分片，不连带已完成的一起重来。

```go
backoff := []time.Duration{0, 10 * time.Second, 30 * time.Second, 90 * time.Second}
for attempt, d := range backoff {
    if d > 0 {
        time.Sleep(d)
    }
    ctx, cancel := context.WithTimeout(parent, 110*time.Second)
    err := runShard(ctx, period, shard, version)
    cancel()
    if err == nil {
        break
    }
    log.Warn("shard failed", "period", period, "shard", shard,
             "attempt", attempt, "err", err)
}
```

单分片超时设置成略小于任务整体超时，避免外层 kill 掉任务时，内层还在跑、状态来不及落库。退避间隔用于应对上游短暂不可用，超过次数就标失败、告警，交人工处理。

并发度需要按实际环境调。分片并发写同一个 MySQL 实例，并发太高会增加锁等待，反而比串行更慢。从 4 开始压测，观察锁等待时间和总耗时，找到拐点。

## 晚到数据的处理

账期截止后留一个补算窗口，窗口内到达的数据走补算流程，生成调整单，不修改原结算单。窗口关闭后还来的数据人工介入。

这条规则要写进结算规则文档，而不只是代码里。代码能挡住技术上的重复计算，挡不住业务方一句「这笔帮我改一下」——账务系统里历史单据不可直接修改，是所有设计的基线。

## 小结

断点续跑的核心不是记住一个位置，而是维护一组带业务语义的状态：哪个账期、哪个分片、哪版规则、跑到什么程度。状态和数据在同一事务里落库，唯一键作为兜底，失败按最小粒度重试。这套结构不复杂，但每一条都是为了保证重算结果和首次运行完全一致。
