# 唯一键挡不住重复付款

「加个唯一键不就幂等了」——这话在系统内部是对的，一旦链路跨出去，就不对了。

代付链路是这样的：

```text
我们 → 云账户（提交指令）→ 云账户异步回调 → 我们更新状态
```

中间任何一步都可能失败，而且失败的方式很不讲道理：请求超时了，但对方其实收到了；回调发过来了，但我们的 HTTP 502 让对方以为没送到，又发一次；查单接口返回成功，同时回调也来了。这些情况唯一键只能挡住「同一笔本地记录写两次」，挡不住「同一笔钱被提交两次」。

## 唯一键的位置决定它挡住什么

假设批次表里给 `batch_no` 加了唯一键。云账户那边收到两笔相同 `batch_no` 的提交，会不会自动去重？取决于对方实现。我们不能假设会。

所以幂等要在两个层面都做：

**本地层**：批次号唯一，状态机单向流转。这张表保证我们自己不会重复提交。

```go
// 只有 PENDING 状态允许提交，任何重复请求撞不到可执行状态
rows, err := db.Exec(`
    UPDATE pay_batch SET status = 'SUBMITTING'
    WHERE batch_no = ? AND status = 'PENDING'
`, batchNo)
if rows == 0 {
    return ErrAlreadyProcessed
}
```

**外部层**：提交指令时携带我们生成的业务单号，对方按这个单号幂等。这是和渠道对接时必须确认的第一个问题，不是「最好有」，是「没有就不能上」。

## 回调重复是最常见的

回调处理逻辑如果写成「收到成功回调 → 更新钱包余额 → 扣减冻结」，重复两次就扣两次。状态机要前置：

```go
// 先占住状态，再做事
affected, err := db.Exec(`
    UPDATE withdrawal_order
    SET status = 'SUCCESS'
    WHERE order_no = ? AND status = 'IN_TRANSIT'
`, orderNo)

if affected == 0 {
    // 已经处理过了，或者状态不对，直接返回成功给渠道
    return nil
}

// 只有抢到状态变更的这次调用，才继续扣钱包、记流水
if err := wallet.ConfirmDeduct(ctx, orderNo); err != nil {
    // 走到这里说明状态已经改了但账务没跟上，必须告警 + 补偿
    alert.Critical("callback state advanced but wallet failed", orderNo)
    return err
}
```

这里有个取舍：把状态更新放在账务操作之前，避免了重复扣款，但引入了「状态成功、账务没跟上」的窗口。反过来先做账务再改状态，重复回调会重复扣款。

我选前者，因为后者的错误是不可逆的（钱已经扣了），前者的错误是可补偿的（跑个补账任务把流水补上）。**分布式系统里选错的方向，不是「哪个更不容易出错」，而是「出错之后哪个能修」**。

## 回调丢失比重复更麻烦

重复通知可以靠状态机挡住，丢失通知没信号。做法是定时查单兜底：

```sql
SELECT order_no, channel_tx_no
FROM withdrawal_order
WHERE status = 'IN_TRANSIT'
  AND submitted_at < NOW() - INTERVAL 2 MINUTE
ORDER BY submitted_at
LIMIT 100;
```

扫到之后主动调渠道查询接口，用查询结果驱动状态机。查单和回调会并发撞到同一笔单子，状态机的 `WHERE status = 'IN_TRANSIT'` 保证只有一个生效。

有个细节：查单间隔不能太密。渠道接口有频率限制，而且对同一笔单子反复查没有意义。我们按 `submitted_at` 做阶梯间隔：2 分钟内的不查，2~10 分钟每分钟一次，10 分钟以上每 5 分钟一次，超过 1 小时转人工。

## 失败解冻的幂等

代付失败要把冻结余额退回来。这个动作同样可能重复执行——回调说失败，查单也说失败，两个线程同时解冻。

冻结记录上带一个 `released` 标记，用唯一约束保证只能释放一次：

```sql
INSERT INTO freeze_release (freeze_id, release_type, biz_no)
VALUES (?, 'FAIL_UNFREEZE', ?)
ON DUPLICATE KEY UPDATE id = id;
-- RowsAffected == 1 才真正执行解冻
```

把「是否处理过」变成一条可查询的记录，而不是一个可以被覆盖的布尔字段。这样出问题时能查到是谁、在什么时间、因为哪个业务单号触发的。

## 还有一类差异查不出来

前面说的都是「同一笔单子重复处理」。还有一类是「两笔不同的单子，金额对不上」：本地记录付了 100 笔共 10 万，渠道回单显示 99 笔共 9.98 万。这种情况没有幂等问题，是纯粹的数据差异，只能靠批次对账发现。

我们的对账是按批次做的：每天拉渠道回单文件，和本地批次明细逐笔比对，差异进差异池。差异池里的单子不自动处理，人工确认后走调整单。这条规矩是踩过坑之后定的——早期自动修复过一次，把一个渠道侧的延迟记账当成丢单，重复发起了一笔代付。

钱的事情上，宁可慢，不要自动。
