# 计费场景下的 95 分位计算

95 峰值是带宽转售里常见的计费口径：把一个账期内所有 5 分钟窗口的速率排序，去掉最高的 5%，取剩下的最大值。这样偶发的突发流量不计入账单，稳定占用的部分才计费。

这个定义听着简单，落到实现上有几个必须明确的地方，否则同一批数据会算出不同的钱。

## 三种分位函数

ClickHouse 里至少有三个函数能算 95 分位：

```sql
quantile(0.95)(rate)          -- 默认实现，reservoir sampling，近似
quantileTDigest(0.95)(rate)   -- t-digest，近似，内存友好
quantileExact(0.95)(rate)     -- 精确排序
```

`quantile` 和 `quantileTDigest` 都是近似算法。它们的共同特点是结果依赖数据的写入顺序和并行合并方式：同样一批数据，分段插入再合并，和一次性插入，质心的位置可能不同，最后一位小数就不一样。

`quantileExact` 的实现是把所有值放进数组排序再取位置，结果只取决于数据集合本身，和顺序、分片、并行度无关。

结算场景要的是后者。原因不是「精确更准」，而是**可复现**：同一个账期重算一次，必须得到和上次完全一样的数。近似算法在监控大盘里够用，在要开发票、要付钱的账单里不够用。

## 数据量其实不大

反对用精确函数最常见的理由是「慢、吃内存」。算一下就知道了：一个节点一个账期（30 天）的 5 分钟窗口数是

```text
30 × 24 × 12 = 8640 个
```

8640 个 float 排个序，几十微秒。真正会让内存吃紧的是高基数 group by：如果把节点、线路、账期、规则版本全部展开，组合数上去之后每个分组各自维护一个数组，内存才会成为问题。

处理办法是分批：一次只算一个账期、一个规则版本，节点分批过，不把所有分组的状态同时放在内存里。这样即使在几千万行的明细表上，精确分位的开销也完全可以接受。

## 舍入位置要写死

窗口速率这样算：

```sql
up_bytes * 8 / 300
```

`up_bytes` 是 UInt64，乘 8 之后仍是整数，除以 300 在 ClickHouse 里得到 Float64。不同写法在小数点后十几位可能不一样，而这些微小差异经过排序后会影响分位值的选取——尤其当两个窗口速率非常接近的时候。

我们的做法是全程用整数 bps，把舍入固定在最后一步：

```sql
toUInt64(up_bytes) * 8 / 300 AS rate_bps
```

在 ClickHouse 的整数除法下 `/` 会截断。截断本身无所谓，重要的是**规则文件里明确写了舍入发生在哪一步**。数学上等价的两种写法，在计费系统里可能算出不同的钱，所以必须选一种、写下来、到处都用这一种。

## 缺失窗口和异常值

节点离线时，那个 5 分钟窗口没有数据。这里有个口径问题：算 0，还是跳过？

- 算 0：会把分位值拉低，等于给离线一种隐性惩罚；
- 跳过：离线完全不影响计费，节点主没有动力保证在线率。

我们选算 0，同时把离线时长单独统计，超过阈值再叠加服务质量的扣罚系数。两件事分开算，不要都塞进分位函数里——混在一起之后，任何一个口径调整都会影响另一个，排查起来非常麻烦。

异常上报（时钟漂移、重复批次）的窗口直接剔除，不进分位计算，但原始记录要保留。剔除规则也要带版本号，和分位算法、舍入规则一起冻结。

## 规则版本化的意义

所有影响计算结果的参数都放进规则版本表：

```go
rule, err := repo.GetRuleVersion(ctx, period, ruleVersion)
if err != nil {
    return err
}
rate := calc.Percentile95(windows, rule.MissingWindowPolicy, rule.OutlierFilter)
```

结算单上记录用的哪个版本。这样任何时候重算，都能用当时的规则复现当时的结果。反过来，读「当前最新规则」去算历史账期，规则一迭代历史账单就变了，这在财务上是不可接受的。

## 边界情况

- 窗口数不足 5% 的样本量时，删掉最高 5% 可能删不掉任何窗口，取到的是最大值。小额节点会出现这种情况，需要单独定义是保留还是按最小值算。
- 分位值后面还要乘扣罚系数，系数是浮点数。金额最终以整数分存储，乘法产生的小数在哪里舍入同样要固定。
- 不同币种、不同结算主体的单价不同，分位值是带宽量，乘以单价才得到金额。这两步要在规则里分开描述。

分位函数本身只是一行 SQL，真正的工作是把围绕它的口径全部定义清楚，并且让代码里的实现和文档里的描述一一对应。
